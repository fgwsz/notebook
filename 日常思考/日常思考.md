# 2026/8/10 关于异常处理携带文件行列信息的思考
在我撰写过的很多`C++`库中都使用了如下的自定义异常类:
```cpp
#pragma once

#include<exception>         //std::exception
#include<source_location>   //std::source_location
#include<string>            //std::string
#include<string_view>       //std::string_view

class Exception:public std::exception{
public:
    Exception::Exception(
        std::string_view const message,
        std::source_location const location=std::source_location::current()
    ):what_(
        std::format(
            "file: {}({}:{}) `{}`: {}",
            location.file_name(),
            location.line(),
            location.column(),
            location.function_name(),
            message
        )
    ){}
    virtual char const* what(void)const noexcept override{
        return what_.c_str();
    }
private:
    std::string what_;
};
```
它的使用方式很简单:
```cpp
throw Exception("这是一个自定义异常");
```
执行上述语句会抛出一个包含如下信息的`what_`字符串:
- 1. `throw`语句所在代码位置信息
- 2. 异常消息信息

这种使用方式看起来是合理的,但是现在遇到了实际使用中的各种问题:

首先,第一个最大的问题是:它返回的位置信息在某些场景下没有太大的意义.

在一些使用场景中,真正对程序调试有帮助,
是在程序抛出异常之前,调用方的代码所在的位置.

也就是什么语句的执行导致了最终的异常抛出.
导致异常抛出的罪魁祸首的语句到底是什么,以及它现在在哪里.

接下来,看一个简单的例子:

如下是一个`JsonValue`类的`get_string()`接口,它在存储值类型是`string`的情况下,
可以正常使用,但是存储类型不是`string`的情况下抛出异常.
```cpp
std::string& JsonValue::get_string(void){
    if(!is_string()){
        throw Exception("Type error:not string!!!");
    }
    return std::get<std::string>(impl_);
}
```
当有人使用这个接口时,无意间触发了异常,来看一下他的调用语句:
```cpp
JsonValue json=R"(
    {
        "Person":{
            "name_":"Tom",
            "age_":20
        }
    }
)"_json;
std::cout<<json["Person"]["age_"].get_string()<<'\n';
//                                ^ 这次调用触发了异常
//正确的调用语句:
//std::cout<<json["Person"]["age_"].get_number()<<'\n';
```
但是此时返回的异常`what()`字符串内容是这样的:
```
file: exception.cpp(114:15) `JsonValue::get_string`: Type error:not string!!!
```
那么我们虽然知道了有人调用`JsonValue::get_string`触发了异常.
但是到底是哪一次`JsonValue::get_string`调用语句触发的呢?

程序源代码中有成千上万的`JsonValue::get_string`调用语句,
而且分散在项目的各个角落.

此时,我灵机一动首先使用`g++ -O0 -g`生成包含调试信息的`Debug`可执行程序.
然后使用`GDB`加断点调试,使用`bt`查看程序崩溃前的函数调用栈,
然后配合`ripgrep`对可疑的函数文件进行搜索,
锁定这些函数中的`get_string`调用语句的位置.
然后逐一加断点排查.

但是这无疑是古法编程时代的最终兵器.一个合理的易用的异常处理并不应该是这样.

`C++23`提供了函数调用栈的获取方式,补齐了这个异常处理的缺陷.

如下是这个函数调用栈的使用案例(来自`cppreference`):
```cpp

#include <stacktrace>
 
int nested_func(int c)
{
    std::cout << std::stacktrace::current() << '\n';
    return c + 1;
}
 
int func(int b)
{
    return nested_func(b + 1);
}
 
int main()
{
    std::cout << func(777);
}
```

我们查看一下`cppreference`中`std::basic_stacktrace`的用法,
发现了如下的2个接口:
```cpp
static basic_stacktrace current( const allocator_type& alloc =
                                     allocator_type() ) noexcept;
//(1)	(since C++23)
static basic_stacktrace current( size_type skip, const allocator_type& alloc =
                                     allocator_type() ) noexcept;
//(2)	(since C++23)
static basic_stacktrace current( size_type skip, size_type max_depth,
                                 const allocator_type& alloc =
                                     allocator_type() ) noexcept;
//(3)	(since C++23)

template< class Allocator >
std::string to_string( const std::basic_stacktrace<Allocator>& st );
```
改进之后的`Exception`类:
```cpp
class Exception: public std::exception {
public:
    Exception(
        std::string_view message,
        std::source_location loc = std::source_location::current()
    ) {
        std::string stack = get_short_stacktrace(3);  // 只取前 3 帧
        what_ = std::format(
            "{}: {}\nCall stack (top {} frames):\n{}",
            loc.file_name(), loc.line(), message, stack
        );
    }
};
```
